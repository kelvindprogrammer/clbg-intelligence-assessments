## B. Problem Statement

A Nigerian electricity distribution company (fictional, "Benue Valley Power") sells prepaid tokens through banks, vending agents and USSD. Its revenue-protection team wants a score for each vend that estimates the chance the meter is being bypassed, so that field teams visit the highest-risk meters first. A data scientist has already trained a small logistic regression. It lives in a notebook, and the plan is to ship it as a pickle file that a web service loads.

Your reviewer is not impressed. A pickle can run arbitrary code on load. A partly written or tampered file would be loaded silently. A vend request from an agent terminal arrives with `"kwh_registered": "52"` as a string, `NaN` as a value, a misspelt meter type, or an extra field nobody documented, and each of these either crashes the service or, worse, produces a confident wrong score. One bad row in a batch of 500 takes the whole batch down.

You are asked to build the **serving contract**, the part of deployment that is plain code and no framework:

1. A **validator** that turns a raw record into a clean, typed record or rejects it with *all* of its problems at once, each with a machine-readable code.
2. A **bundle**: the fitted model and its preprocessing stored as plain JSON (no pickle) with a version and a SHA-256 checksum, loaded only after the checksum and format version are verified.
3. A **prediction function** that scores a batch, returns one result per input in the same order, and never lets one malformed record fail the others.

The data is synthetic (generated by `resources/datagen.py`). You will not tune the model; the learning goal is the contract around it. The specification is precise, and the tests check it exactly.

> **Why this matters beyond this task.** Most production ML incidents are not model errors. They are contract errors: a changed field type, a silent default, an unverified artefact. A model service is only as trustworthy as its smallest validation rule.

## C. Objectives

When you finish, you should be able to show that you can:

1. **Specify** an input schema precisely (types, ranges, categories, required fields) and enforce it, reporting every violation with a stable code.
2. **Serialise** a fitted model and its preprocessing as plain JSON, and explain why that is safer than pickle.
3. **Protect** an artefact with a checksum and a format version so that corruption and incompatible files fail loudly.
4. **Isolate** failures in batch prediction so one bad record yields one error result, not an outage.
5. **Compute** a logistic score in a numerically stable way and show it is independent of batch composition.
6. **Test** a serving function against hostile inputs, not just the happy path.

## D. Technical Requirements

### D.1 Mandatory functional requirements

Implement `modelpack` in [`starter/modelpack/`](starter/modelpack/). Use only numpy and scikit-learn (plus the standard library). The schema format is the dictionary `SCHEMA` in [`resources/datagen.py`](resources/datagen.py): each field has a `type` (`float`, `int` or `category`), numeric fields have inclusive `min` and `max`, and categories have an `allowed` list. Every field is required.

| ID | Requirement |
|---|---|
| **R1** | `validate_record(record, schema) -> dict`. Returns a cleaned dict containing only schema fields in schema order, with numbers coerced (`float` fields to `float`, `int` fields to `int`). Raises `ValidationError` (already defined) carrying **all** `(field, code)` pairs. Codes: `missing` (absent or `None`), `unknown` (field not in the schema), `type` (not a number, a `bool`, an unparseable string, or a non-integral value for an `int` field), `range` (non-finite, or outside `[min, max]`), `category` (not a string in `allowed`; case-sensitive). Numeric strings such as `" 5000 "` are accepted and coerced. A non-dict record raises a single `("<record>", "type")`. |
| **R2** | `fit_bundle(records, y, schema, version)` validates records, standardises numeric fields with the **training** mean and standard deviation (a zero standard deviation becomes 1), one-hot encodes categories using **sorted** `allowed` levels, fits `LogisticRegression(C=1.0)` and returns a JSON-serialisable `dict` with keys `format_version` (1), `version`, `schema`, `preproc`, `weights` and `bias`. `encode(clean_record, bundle)` returns the feature vector in the bundle's fixed order. |
| **R3** | `save_bundle(bundle, path)` writes a JSON file `{"payload": bundle, "sha256": ...}` where the digest is the SHA-256 of the canonical JSON of the payload (sorted keys, separators `,` and `:`). `load_bundle(path)` raises `IntegrityError` if the digest does not match, and then `UnsupportedVersion` if `format_version != 1`; otherwise it returns the payload. |
| **R4** | `predict(bundle, records) -> list[dict]`. One result per input, same order. A valid record gives `{"ok": True, "score": p, "model_version": v}` with `p` the probability in `[0, 1]`; an invalid one gives `{"ok": False, "errors": [[field, code], ...]}`. The score of a record must not depend on the other records in the batch. The sigmoid must not overflow for extreme inputs. An empty batch returns `[]`. |

### D.2 Engineering requirements (mandatory)

- Nothing may be unpickled, `eval`-ed or `exec`-ed; the saved file is data only.
- `validate_record` must not mutate its input; `fit_bundle` must not mutate the records it is given.
- At least **8 tests of your own** in `tests/test_member_*.py`, including a fuzz test (random junk values never raise anything except `ValidationError`) and a test that `load_bundle` rejects a file with one changed digit.
- `REPORT.md` explains each design decision in the sections below.

### D.3 Responsibility

The data is synthetic and no real customer appears. In the report, write one paragraph on what a *false* bypass flag costs a household (a field visit, a disconnection threat, reputational harm) and what an error code returned to an agent terminal must *not* reveal (internal paths, other customers' data). Mention the NDPA 2023 principle of data minimisation in relation to which fields the service logs on failure.

### D.4 Optional enhancements

- Reject JSON bundles whose weights contain `NaN` or whose length disagrees with the encoded features.
- A `schema_hash` stored in the bundle so a caller can detect a schema change.

## G. Acceptance Criteria

The submission is **accepted** only when every criterion below holds. Criteria marked ⚙ are checked by the public and hidden test suites; the rest are checked by hand.

1. ⚙ `pytest` passes the provided tests and your own from a clean environment.
2. ⚙ `validate_record` returns exactly the specified `(field, code)` pairs for each hostile case in the public tests, including `bool`, `NaN`, `"inf"`, non-integral `int` values, `None` and unknown fields.
3. ⚙ A bundle saved and loaded gives bit-identical scores; changing one weight in the file raises `IntegrityError`; a valid file with `format_version` 2 raises `UnsupportedVersion`.
4. ⚙ **Quality.** On the 1000 held-out public records the bundle's ROC-AUC is at least **0.75**. *Justification:* the reference reaches about 0.83; the signal is linear by construction, so a correct standardise-and-fit pipeline must clear 0.75 and a broken encoding (for example, unsorted or mismatched levels) does not. Hidden seeds use 0.72 because of sampling noise (about ±0.02 at n = 800).
5. ⚙ **Isolation.** A batch containing invalid records returns results in input order, with invalid ones marked `ok: False` and valid ones unchanged from scoring them alone.
6. ⚙ The saved file is JSON with exactly the keys `payload` and `sha256`; no pickle.
7. ✍ The report states why pickle is unsafe and what the checksum does and does not protect against (it detects corruption, not a deliberate attacker who can also rewrite the digest).
8. ✍ The report lists three failure modes your validator prevents and one it cannot (for example, a valid but drifted distribution).

## Pedagogical Design

*This section explains the design of the assessment for members, mentors and assessors.*

| Question | Answer |
|---|---|
| **Knowledge needed** | Python dicts, exceptions and JSON; fitting a logistic regression. No web framework, no deployment tooling. |
| **New skill developed** | Treating a model as an artefact with a contract: strict inputs, verified storage, isolated failures. |
| **Decisions the member must make** | How to coerce versus reject; how to order and collect errors; how to canonicalise JSON for the digest; how to keep scoring independent of the batch. |
| **What must be investigated independently** | Why `bool` is a trap for numeric validation, how floats behave at overflow, and what a checksum does and does not defend. |
| **Why it is interesting** | The model is the easy part. The interesting work is the dozen rules that make it safe to expose. |
| **Evidence of competence** | Exact error codes on hostile cases, tamper detection, order-preserving isolation, re-seeded quality. |
| **Misconceptions exposed** | 'Pickle is fine for internal use.' 'A checksum makes a file trustworthy.' 'Validation means checking the type.' 'The batch should fail if any row is bad.' |
| **Preparation for later work** | Leads into ML-12 Tier 2 (serving under latency constraints) and Tier 3 (rollout and rollback), and into ML-13 monitoring. |
